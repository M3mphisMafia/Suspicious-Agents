              White paper — how Undertow Security works

              The problem

              Autonomous AI pentest agents (ARTEX and its forks) are driven by a language model in a loop: it reads a target's responses as context, decides the next action, calls a tool, observes the result, and plans again. They chain known weaknesses at machine speed, rotate IPs and user-agents, and — crucially — believe what they read. Signature scanners miss them because there is no fixed payload; the behavior is the tell.

              Detect

              Undertow keys on behavior, not signatures: the burst-then-think cadence of a model reasoning between actions, self-correction after a 422, reading the API map then targeting it, walking sequential IDs, hopping login routes, and ignoring Retry-After. Each detector returns an independent probability; they combine as 1 − ∏(1 − w), so evidence only escalates. An actor is keyed by /24 + user-agent (+ TLS fingerprint for spoofed browsers), so IP rotation does not reset it.

              Ground truth

              A hit on a decoy route, a planted honey token, a cell-minted ID, or the canary AWS key is a certain attacker — no legitimate user does this. That certainty is the ruler the system measures everything else against, and it is what auto-tuning learns from.

              Slow

              Flagged agents get 429 + Retry-After: 9 (which pauses the agent's own governor for the whole host), uniform errors (so it cannot self-correct), and tarpit delays that eat its ~600-second per-objective budget.

              Deceive — the padded cell

              A confirmed agent is not blocked (a block is something it routes around); it is quietly moved into a fake copy of the app that seems to work: logins succeed, writes are accepted and discarded, lists page on forever, export jobs sit at “almost done”. It is generated deterministically from (agent tag, path), so the world is consistent for one agent across IP rotation, and a little inconsistent over time — which the model chases as a finding. Real users never see it.

              Drain — the token sink

              The agent reads every response into its model as context. Each cell response is padded with dense, plausible data up to just under its ~30 KB tool-output cap, so every fetch costs it the maximum input tokens. Serving this costs us microcents and zero storage (it is generated, not stored); processing it costs the attacker real tokens — money on a paid API, time and compute on a home model. The asymmetry favors the defender. The goal is economic: make this target cost 10× for zero yield, so at scale it is the one they skip.

              Judge

              The Judge, a large language model, reviews the agents near the line every two minutes, reading their behavior as untrusted data. It can only raise suspicion, never clear anyone, and (in Act mode) its verdict counts as one more detector signal. It runs on the engine's default model (DEFAULT_MODEL in aa_ai/__init__.py) unless an operator deliberately sets another; flood mode uses the same model.

              Floods and edge rules

              A bot flood is volume, not an agent, so it is blocked, never deceived. AWS Shield Standard absorbs network floods, AWS managed rules in the web ACL stop web floods, known attack sources and known exploit payloads, and Undertow's flood mode blocks the IPs driving a surge and can add one narrow edge rule. Generic signature rules only label requests: Undertow lets agents in so it can deceive and drain them. See Flood mode below.

              Cost

              About $50 a month for a typical install, mostly the firewall. The Budget page estimates it hourly and checks it against the bill daily; a budget alarm emails you at $100. See Costs and budget below.

              Learn

              Auto-tuning measures, per detector, how often it co-fires with a certain catch versus on agents an operator later unblocks, and suggests a weight from that precision. It is bounded to 0.5–1.5×, needs 8+ observations, and never touches the certain detectors — so one noisy run can never disable a detector or let it dominate.

              Components

              Everyone enters the same edge. It routes normal traffic to the real app, confirmed agents to the padded cell, and bait hits to the decoys, while the control plane watches the logs and reconfigures the edge. The scorer reads the WAF logs; a separate 1-minute tick runs flood mode, the WAF sync, costs and this dashboard, so a flood can never starve it.

              User's manual

              Getting around

              • The console opens on Dashboard. Reloading the page keeps you on the tab you were on, and on the time range you chose, even after you sign in again.
              • ↻ Refresh at the top loads the latest data for the tab you are on right away, including the user list and the integrations. The live scene has its own ↻ Refresh, which also works in full screen. Everything updates on its own every minute too.

              Reading the attack

              • Dashboard — the live scene: requests as lights crossing the edge into your app, for a big screen. Admins see the live feed; see Dashboard below.
              • Overview — the glance: requests inspected, agents flagged, decoy hits, attacker time burned, the live-traffic view, the Allow → Watch → Tarpit → Block ladder, out-of-norm alerts, the padded-cell count, and flood mode.
              • Agents — each flagged attacker: score, verdict, the detectors that fired, a score-over-time chart, detector accuracy, and the Judge's verdicts.
              • Deception — the padded cell (who is trapped, requests absorbed, agent-minutes wasted, tokens burned) and the board of their move → our counter.
              • Budget — what the install costs this month by service, the projection to month-end against the $100 budget, and how the estimate compares with the real bill (see Costs and budget).

              Tuning the defense (Controls)

              • Enforcement — Observe scores but never blocks; Enforce applies the edge decision. Edge modes: Cell (route confirmed agents to the fake app — default), Certain (429 at the edge), Suspects (block suspects too), Lockdown (block anything above the watch line — for an active attack).
              • Edge controls — live edge knobs: auth rate limit, Retry-After seconds (on every edge 429, the lead-form limit included), block by country or network, challenge sensitive requests.
              • Tuning — move the Watch / Tarpit / Block thresholds and set a 0–2× weight per detector. The green “→” is the weight auto-tuning suggests from confirmed catches; Auto-tune applies suggestions automatically, or use Apply suggested now once.
              • Alerts — toggle which events email you. Exceptions and audit — unblock a false positive, release a challenge, and see every operator action.

              Per-agent actions

              On Agents, each attacker has Block / Challenge / Tarpit / Unblock. The Judge has Advise (records only) and Act (its verdict counts toward the score).

              Users

              Invite teammates (admin or view-only); the system emails a one-time password. Admins sign in with an authenticator app; Reset MFA lets someone who lost their device set up a new one.

              Testing with ARTEX

              The attack runs from a separate test runner with its own IP, outside the app. Drive its intensity from 0 to 6 (0 off · 5 fast · 6 flood). The dashboard shows its effect; it never connects to the agent.

              Protecting other apps

              One engine can protect other apps on their own CloudFront distributions. Each one shares the engine's web ACL, cell router and padded cell (infra/protect-app.yaml), so its traffic is scored, blocked and moved into the cell by the same rules, flood mode included. List each app in infra/apps.json; it then shows by its host under Controls → Integrations.

              What it is, and is not

              • A sample, not every request. Each batch of WAF logs keeps at most 40 requests, rare kinds first (decoy hits, known agents, challenges, verified clients), so a quiet minute and a flood both look right. The density follows the real counts for the minute.
              • One to two minutes behind. WAF logs reach Undertow within a minute or so, and the scene refreshes once a minute and replays the latest minute at its real pace.
              • Admins only. The live feed carries IP addresses, so only admins (signed in with an authenticator app) receive it. Everyone else, and the page opened from disk, sees synthetic demo traffic from documentation IP ranges, labeled as such.
              • The samples are kept for 2 hours. With reduced motion turned on in your system, the scene stays still and shows the counts instead.

              Flood mode and edge rules

              A bot flood is not an attack agent

              An ARTEX-class agent is one model-driven client working low and slow: it reads every answer, plans, and adapts. Undertow catches it by behavior and deceives it in the padded cell. A bot flood is volume: thousands of scripted clients, often a botnet or rented proxies, hitting the same pages to exhaust the app or its bill, with each IP kept under the per-IP rate limit. Floods are blocked, never deceived: a flood is never routed to the padded cell.

              Three layers

              • AWS Shield Standard, on for every CloudFront distribution at no charge, absorbs network and transport floods (SYN floods, UDP reflection) before there is any HTTP to inspect.
              • Managed rules in the web ACL. The AWS anti-DDoS rule group learns this site's normal traffic and, during a layer-7 flood, silently challenges suspect clients and blocks the worst. The AWS IP reputation list blocks addresses AWS threat intelligence has seen attacking. The per-IP rate rule (2,000 requests per 5 minutes) sits beside them.
              • Undertow flood mode, on top, for a flood spread so wide that no single IP trips a limit.

              More protections in the web ACL

              Known bad inputs (Log4j, Java deserialization and similar exploit payloads) blocks; Undertow still records those requests as attack evidence. The core rule set, SQL injection and anonymous IP rules only count: they label requests in the WAF logs and change nothing else, not even an agent's score. That is on purpose: Undertow lets agents in to deceive them and drain their budget, and blocking on a generic signature this early would hide what they came to do. The lead-form limit blocks a client after 10 posts to /api/lead in 5 minutes (429 with Retry-After).

              What flood mode does

              • It runs on the 1-minute tick, a function of its own, apart from the one that reads the WAF logs: however busy a flood keeps the log reader, the tick still runs every minute. Under a flood the log reader also stays cheap: during a surge, a source past 120 requests in a minute is counted but its further requests are not stored or re-scored, at most 50 agents a batch are re-scored, and the WAF sync is left to the tick. Outside a surge every request is scored, because agents run at machine speed. Flood mode decides from those counts, never from stored requests.
              • Every minute it compares the last full minute with the median of the 30 before it. Minutes already in a surge are left out, so a long flood never becomes the norm. A surge is at least 5 times that norm and at least 600 requests a minute.
              • During a surge, any IP at 120 or more requests in the minute is blocked at the edge for 15 minutes (429 with Retry-After), renewed while it keeps flooding, up to 5,000 IPs. Allow-listed and verified clients are never blocked. This holds in every edge mode, the padded cell included.
              • If the surge lasts 2 minutes or more and the blocked IPs carry less than half of it, flood mode looks at what the rest of the traffic shares (user agent, JA4 TLS fingerprint, path, host) and adds one edge rule on a value that carries at least half of it: a Challenge by default, for 30 minutes (60 at most). The rule goes when it expires or about 10 minutes after the surge ends, and the scorer puts it back within a minute if a deploy resets the web ACL. Your console under /_undertow/ is never matched.
              • Requests from IPs flood mode already blocks, and requests the flood rules already stopped, are counted but not stored, so a flood does not turn into a database bill.
              • One alert when a surge starts and one when it ends. In Observe it records what it would do and changes nothing at the edge.
              • These defaults are starting guesses, not measured values: tune them after a real flood. Change them with the policy API: set_policy with a flood object (enabled, act, pattern act, advise or off, multiplier, floor_rpm, per_ip_rpm, ttl_minutes, pattern_minutes, max_ips). Turning it off releases its blocks at once.

              What the LLM does, and does not do

              Statistics detect the surge and block the IPs. The LLM (the judge's model, the engine's default unless an operator sets another) is only asked to pick the one pattern rule, from values seen in the last minute that already carry at least half the traffic, and it reads them as untrusted data. The code enforces the limits whatever it answers: the value must be one of those seen, Challenge is the default, Block is allowed only for a user agent that is plainly a script (curl, python, Go, Java, wget, headless browsers and the like), and the path / alone is never matched. If it errors, times out or answers badly, flood mode challenges the top value only when it carries 60% or more, and otherwise does nothing. It is asked at most once a minute during a surge and 10 times an hour. It never sees, and never answers, a live request.

              Testing it

              • Use a test stack in Observe. Lower the lines for the test, for example floor_rpm 60 and per_ip_rpm 30, so a small test trips them.
              • From a few machines you control, send steady requests above per_ip_rpm (and well under the per-IP rate rule) with a plain client such as curl, for 3 minutes or more.
              • Within about two minutes this card shows a surge and the IPs it would block; two minutes later, the rule it would add. Switch to Enforce to see the 429s and the rule at the edge.
              • Put the defaults back afterward. Keep tests small: a full-scale flood is a DDoS simulation, which AWS allows only through its approved testing partners.

              Cost

              • AWS anti-DDoS rule group: $20 a month plus $0.15 per million requests. Requests it blocks are not billed as WAF requests.
              • AWS IP reputation list: $1 a month.
              • Known bad inputs, core rule set, SQL injection and anonymous IP: $1 a month each, the rule charge.
              • Flood mode adds no fixed fee: a database write per IP per log batch, a few more each minute of a surge, at most 10 LLM calls an hour during a surge, and the pattern rule bills as one more WAF rule only while it exists.

              Costs and budget

              What it costs

              A typical install costs about $50 a month in AWS charges, most of it the firewall: the web ACL ($5), $1 a month for each rule and managed rule group, and the AWS anti-DDoS rule group ($20 a month plus $0.15 per million requests). The rest is CloudFront, Lambda, DynamoDB, logs, the reference store's Secrets Manager endpoint (billed by the hour) and the LLM calls of the judge and flood mode. It is not free when idle.

              The budget alarm

              An AWS budget emails the alert address when actual spend passes 80% of $100 in a month, and again when the month is forecast to pass $100 (MonthlyBudgetUsd changes the amount; it needs AlertEmail). It covers AWS WAF and CloudFront for the whole account: other web ACLs and distributions in the account count toward it too.

              The Budget page

              Estimated hourly. Once an hour the 1-minute tick reads the engine's own usage from CloudWatch (its web ACL, its CloudFront distributions with protected apps included, its Lambda functions, its table and its WAF log group) and prices it at us-east-1 list prices. The page shows the month so far, the daily cost by service, and a projection to month-end from the last day's run rate. The prices, and the few usage figures CloudWatch cannot give, are assumptions listed in aa_ai/costs.py.

              Verified daily. Once a day the tick checks the estimate against the real bill from Cost Explorer, by service and for the same days. That takes at most two Cost Explorer calls a day, at a cent each. The bill reaches Cost Explorer about a day late.

              Exact or account-wide

              Every Undertow stack is tagged undertow=engine. Exact means that tag is an active cost allocation tag, so the check counts only resources that carry it (the reference store included). Tags count from activation on, so a check is exact from the first full month after it. The tick tries to activate the tag once a day; in an AWS Organizations member account the management account may have to. Account-wide means the same services across the whole account, so other workloads count too and the bill reads higher than the estimate. LLM calls are billed under the model's own name and carry no tag, so they are estimated only.
